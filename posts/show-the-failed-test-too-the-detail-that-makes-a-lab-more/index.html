Show the Failed Test Too: The Detail That Makes a Lab More Believable

A failed test can make an IAM lab more convincing when you show what was wrong, how you investigated it, and what the retest proved.

An error screenshot alone doesn't do that. Neither does inventing an outage to make a simple exercise sound dramatic.

Keep the evidence connected: expected behavior, observed mismatch, justified correction, and a checked result. That lets a reviewer follow your reasoning instead of taking your conclusion on trust.

Record the expectation before the result

Suppose a fictional contractor should read a project folder but not modify its contents.

Write that expectation before testing. Then record what actually happened under the contractor's account.

If modification succeeds unexpectedly, you have a meaningful mismatch. The test is useful because the expected behavior was defined independently of the outcome.

A screenshot with an error message and no stated expectation is much harder to interpret. The reader can't tell whether the error is the problem or the intended security control.

Preserve enough context to explain the failure

Capture the account context, resource, action, and relevant configuration state using fictional or sanitized data.

You don't need to publish every diagnostic detail. You do need enough information to show why you investigated the permission path rather than changing an unrelated setting.

Keep a private working note of the hypotheses you considered. In the public summary, distinguish what you observed from what you suspected.

That distinction makes the troubleshooting account more credible than a polished story in which every first guess was correct.

Explain the change that mattered

Perhaps the contractor inherited broader access through an additional group. Your evidence should identify that path and explain why removing the membership was appropriate for the scenario.

Don't write “fixed permissions” when you can describe the actual decision.

Also explain what you did not change. If the user's authentication was already working, say that the correction concerned authorization rather than a password issue.

The reader should understand the cause-and-effect claim you're making.

Retest the allowed action and the action you meant to block

Suppose a contractor should read project files but not change them. After correcting the permissions, test both sides of that requirement.

Retest Expected behavior
Open the intended project document Allowed
Modify that document Denied

Blocking everything might eliminate unwanted modification while also preventing legitimate work. It isn't a successful correction of this requirement.

Use the appropriate fresh session or context and record the test conditions. Keep them comparable with the original test.

Also confirm that each attempt reached the intended resource. A denial caused by a mistyped path doesn't demonstrate that your authorization rule worked. The meaningful evidence is the relationship between the requirement, the correction, and the observed behavior—not the appearance of an error message.

Show the failed test without overwhelming the page

A concise before-and-after table is often enough for the main article:

Stage Read project file Modify project file
Initial test Allowed as intended Allowed unexpectedly
After correction Allowed as intended Denied as intended

Link the supporting screenshots or sanitized outputs below the table. The reader can inspect them without losing the main story.

If the failure was deliberately introduced, label it as a controlled fault test. Don't present it as an accidental incident you heroically rescued.

Use the result to explain a broader lesson carefully

You can conclude that the example taught you to inspect effective access rather than trusting a group label. You cannot conclude that one lab proves expertise in every authorization system.

State the limit and identify a sensible next test. Use honest troubleshooting documentation to avoid turning the write-up into invented drama.
