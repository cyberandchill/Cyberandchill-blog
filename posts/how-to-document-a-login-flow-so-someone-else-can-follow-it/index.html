How to Document a Login Flow So Someone Else Can Follow It

A login-flow diagram should let someone follow one tested sign-in from the user's action to the application's access decision.

Product logos connected by arrows labeled “authentication” aren't enough. Name the participants, explain what each receives or decides, and connect important stages to evidence from your lab.

Keep the first view simple. Detailed protocol notes can sit below it without making a reader reconstruct the whole flow from configuration screenshots.

Name the participants before drawing the arrows

Start with the user agent, the identity provider, the application, and any separate resource relevant to the scenario.

Use plain-language labels alongside product names. A reader should understand the role of each component even if they haven't used the exact platform.

Keep the scope narrow. If your lab uses one application and one identity provider, don't add every possible service from an enterprise reference architecture.

A diagram is useful when it explains the environment you actually tested.

Number the observable stages of your tested flow

Describe the major stages in the order they occur:

  1. Start: What user action begins the attempt?
  2. Authentication: Where is the identity checked?
  3. Return: What does the supported integration send back to the application?
  4. Application outcome: How is the session or permitted access established?

The exact sequence depends on the protocol and integration. Check the relevant vendor documentation; don't assume every SSO setup follows an identical path.

Keep each step short enough to sit beside the diagram. Put details that interrupt the first explanation in a separate note.

Most importantly, distinguish behavior you observed from behavior described in documentation. A copied theoretical diagram doesn't by itself prove your lab followed that path. Make your verification and any unobserved steps clear.

Label the decisions, not just the communication

An arrow shows that information moves. It doesn't explain what the receiving system decides.

Add a short label for the relevant validation or access decision. For example, distinguish the identity provider's authentication result from the application's decision about the user's role.

Avoid publishing actual tokens, credentials, or sensitive claims. Use invented or redacted examples where a message format is useful to explain.

The reader needs to understand the trust relationship, not receive a reusable authentication artifact.

Attach one piece of evidence to each important stage

You might use a sanitized log reference, a test observation, or an application result.

Explain what each item proves and what it does not. A successful identity-provider event doesn't prove the user completed every application action. A browser error doesn't necessarily identify the system that caused it.

Correlate the evidence to the same test attempt where your tools allow it. Record the time and context so unrelated events don't accidentally become one story.

Keep detailed logs behind descriptive links rather than crowding the diagram.

Show the controlled failure on the same map

After establishing the baseline, identify the stage affected by one safe lab misconfiguration.

Mark where the observed flow diverges from the expected one. Then explain the relevant correction and the recovery test.

This is more informative than creating a second diagram with a large red cross over the entire application.

Use a staged SSO investigation to keep the failure explanation connected to evidence rather than a guessed cause.

Add a short reader's guide beneath the diagram

Include the scenario, the protocol or method used, the test identities, and the project's exclusions. Keep identities fictional and avoid exposing your actual tenant or personal environment unnecessarily.

State which parts you implemented and which are conceptual. If the application uses local authorization that your lab doesn't test, say so.

Then practice explaining the diagram without reading every label. A good visual should support your explanation, not replace understanding of the flow.
