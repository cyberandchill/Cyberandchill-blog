A Lab Should Answer a Hiring Question. Here's How to Pick One.

Before building a lab, write the hiring question its evidence should answer.

“Can this person explain why one user gets access and another doesn't?” gives you a clearer project than “Can this person install several tools?” It defines the purpose, test, and stopping point.

Choose the question from a responsibility in a role you'd consider. Then build the smallest scenario that provides a credible answer rather than expanding the infrastructure first.

Convert a job responsibility into an evaluation question

Start with one central duty and ask what evidence would show capability.

Responsibility Question to answer
Troubleshoot application sign-in Can I follow the path, locate a controlled failure, and verify a correction?
Support employee lifecycle changes Can I show how a transfer affects access and check removal of obsolete permissions?
Administer resource access Can I explain and test the boundary for the intended users?

These questions are narrower than “Do I know IAM?” and still require reasoning beyond installation.

Keep the original duty beside the project question. That preserves the connection when the technology becomes interesting and new features tempt you to expand the scope.

A finished project should let you answer the question with evidence, not merely point to an environment and hope the capability is implied.

Decide what evidence would change someone's mind

Imagine a skeptical but fair reviewer. What would they need to see before accepting your claim? For a sign-in project, that might include the flow diagram, a successful baseline, a controlled error, relevant evidence, and a retest after the correction.

For a lifecycle project, it might be a before-and-after access matrix and a record of the changes you verified.

A product installation screenshot may be part of the setup, but it rarely answers the evaluation question on its own.

List the evidence before choosing the rest of the tooling.

Keep the scenario small enough to explain

Use one fictional business situation. For example, a contractor needs temporary read access to a project resource. Define who approves it, what access is allowed, and what should happen at the end of the assignment.

You can represent the workflow with a modest lab and documented steps. You don't need to build an entire enterprise governance platform just to explain the lifecycle logic.

The business-scenario-first approach to choosing identity tools helps keep the environment from growing beyond the question.

Include one condition that could disprove your claim

A test should have a meaningful chance to reveal that your implementation is wrong.

If the contractor should have read-only access, attempt an action that should not be permitted. If access should end, test again after the removal process under documented conditions.

Don't count a generic network error as proof of authorization. Establish a control that shows the resource and test path are functioning.

This makes the project more than a demonstration of the happy path. It shows that you understand the boundary you're trying to enforce.

Write the project summary as an answer

Your first paragraph should answer the original hiring question in bounded terms.

“This lab demonstrates a temporary-access workflow using fictional identities. It records approval, applies read access, checks an unauthorized action, and verifies removal in a fresh test session.”

Then show the evidence and limitations. Avoid broad claims about production readiness or business impact that the exercise cannot support.

A reader should understand the purpose before seeing a list of versions, commands, or screenshots.

Stop when the question has been answered well enough

Once the required evidence is complete, publish a sanitized version and practice explaining it.

Additional ideas can become a backlog. They don't all belong in the first version.

If a new feature answers a different hiring question, consider making it a separate project rather than turning one portfolio item into an unfocused collection.

This also makes interviews easier: you can select the example that matches the question instead of trying to explain everything you've built at once.
