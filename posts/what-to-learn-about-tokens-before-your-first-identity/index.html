What to Learn About Tokens Before Your First Identity Interview

Before memorizing token fields, learn who issued the token, who should accept it, what it is for, and how trust is checked.

Decoding a token can reveal information about its structure. It does not prove that the token is valid or appropriate for a particular application.

For an identity interview, prepare to explain the purpose and validation boundary. Use documented examples in a test environment, and treat live tokens as sensitive material rather than portfolio screenshots.

Distinguish an ID token from an access token

In an OpenID Connect flow, an ID token gives the client application information about an authentication event and the user. An access token is used when calling a protected resource such as an API.

They are not interchangeable. Microsoft's documentation distinguishes ID tokens from access tokens and warns against using an ID token as the credential for an API call.

In an interview, explain the intended recipient and purpose rather than saying both are simply “proof the user logged in.”

Explain why the audience matters

A token intended for one application or API should not be treated as permission to access every other service.

The recipient needs to evaluate whether the token was issued for it and whether the relevant authorization conditions are satisfied.

For a learning exercise, draw the client, issuer, and resource. Label which component receives which token and why.

That simple diagram can expose confusion that a list of claim names hides. You should be able to follow the credential through the flow without assuming that every component has the same responsibilities.

Explain why reading claims does not validate a token

A token in a readable format such as JWT may contain plausible-looking claims. That alone doesn't establish trust.

Distinguish these questions:

Inspection Validation
What does the token appear to contain? Has its integrity been checked appropriately?
Which issuer or audience is named? Are those values acceptable for this recipient and purpose?
Which times are shown? Does the token meet the applicable time conditions?

The required checks depend on the token type and protocol. Use supported libraries and current provider guidance rather than building your own production validator as a beginner exercise.

In a lab, identify which component performs validation and what your demonstration actually observes. Reading a token's contents is a learning aid, not a replacement for the application's trust decision.

Do not assume every access token is readable

A client should not depend on decoding an access token to decide how the API will treat it.

Microsoft advises client applications to treat access tokens as opaque and leaves validation to the resource that accepts them. The format may not be something the client should interpret.

That is an important distinction when discussing troubleshooting: you can inspect the flow and returned metadata without making the client responsible for interpreting a credential intended for another component.

Use the provider's supported diagnostic approach rather than assuming all tokens have the same shape.

Treat token handling as credential handling

Do not publish live tokens, refresh tokens, or session cookies in a portfolio, screenshot, or public decoding service.

Use synthetic examples or carefully controlled non-sensitive documentation. A token can be useful to someone else while it remains valid, so its unfamiliar appearance does not make it safe to share.

The publication review for identity labs should include authentication traces and hidden supporting files, not just obvious password fields.

Also avoid assuming that signing out of one application instantly invalidates every credential or session. The behavior depends on the system and must be verified.

Prepare one clear explanation and one bounded example

A useful answer is: “I first identify the token's purpose and intended recipient. Then I check which component validates it and which authorization decision follows. I do not treat decoded claims as proof of validity.”

Support that answer with a small test flow you actually understand. State what you did not test.
