One Login, Three Systems, Five Places It Can Break

A correct password doesn't guarantee a working application login. The failure could occur before authentication, during the identity-provider checks, at the application handoff, or when permissions are evaluated.

Start with the last stage you can confirm succeeded. That is more useful than changing credentials every time the user sees an error.

Map the browser, identity provider, and application first. Then investigate the failing handoff using evidence from the systems you're authorized to inspect.

Start with a simple three-system picture

For this example, use a browser-based application that redirects sign-in to an identity provider.

The browser carries the user through the flow. The identity provider checks the user and the applicable sign-in conditions. The application consumes the returned identity information and applies its own access rules.

This is a simplified model, not a claim that every SSO architecture has only three components. Proxies, directories, provisioning services, and additional policies may participate.

Microsoft's SAML protocol documentation shows the request, response, and validation elements behind one common federation flow.

Failure point one: The browser cannot reach the intended service

Before investigating identity claims, confirm the user reached the correct application and identity-provider endpoints.

Name resolution, connectivity, certificate trust, or an incorrect application address can stop the flow before authentication begins.

Record the destination and the visible error without publishing sensitive URLs or session data. A browser failing to load a page does not establish that the user lacks permission.

In a lab, keep a known-good baseline so you can distinguish an identity change from an unrelated connectivity problem.

Check why the identity provider rejected the attempt

If the request reached the identity provider, narrow the investigation to the checks performed there.

Question Why it matters
Was this the intended account? A different account can produce a different result.
Was the account allowed to authenticate? Account state may explain the rejection.
Which authentication or access requirement failed? Credentials are only one possible cause.
Can you match the event to the attempt? The wrong timestamp or event can mislead the diagnosis.

Record the test identity, approximate time, and relevant correlation information in private notes where appropriate. Use sanitized evidence in public documentation rather than copying real sign-in records.

The goal is to identify the failed check, not to disable protections until the application opens. Correct the demonstrated cause within the scope of your lab or authorized support procedure.

Failure point three: The application rejects the returned identity information

Successful authentication does not guarantee the application accepts the response.

In a SAML example, the application must validate information such as the intended audience, issuer, signature, and relevant time conditions. Configuration mismatches can therefore break an integration after the identity provider has authenticated the user.

For a controlled lab, change one documented setting and observe where the failure appears. Restore the setting and retest.

Do not “fix” a failed test by disabling security validation. The point is to understand the agreement between the systems.

Failure point four: The application cannot map the user correctly

The application may receive identity information but not associate it with the expected account or role.

Investigate which identifier or attribute the application expects and whether the integration supplies it in the intended form. Keep provisioning and sign-in separate in your explanation: creating an account and authenticating a user are related but different tasks.

A clear diagram of the login flow and its handoffs helps show where this mapping occurs.

Use fictional identities when you demonstrate the problem publicly.

Failure point five: The user signs in but cannot perform the action

Reaching the application does not mean the user is authorized to do everything inside it.

Test the actual operation: opening a record, editing a file, or using a protected function. Compare the expected role with the application's effective access decision.

A login-success screenshot is incomplete evidence when the requirement concerns a particular resource or action.

Turn the investigation into a useful project

Your project notes should show the baseline, the changed condition, the failing stage, the evidence, and the successful retest. Avoid a diary of random settings you tried.
